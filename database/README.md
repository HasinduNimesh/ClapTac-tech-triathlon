# Database

Waypoint uses **one PostgreSQL instance** in Milestone 1.

Logical schema ownership:

| Schema | Owner service |
|---|---|
| `orders` | order-service |
| `planning` | planning-service |
| `fleet` | fleet-service |
| `loading` | loading-service |
| `delivery` | delivery-service |
| `shared` | shared-service (also the product catalog) |
| `audit` | shared-service |
| `inventory` | inventory-service (planned; tables only for now) |
| `ai` | insights-service (planned; tables only for now) |

Services must not query another schema. Example: delivery-service must not `SELECT` from `orders.orders`; it calls Order Service over HTTP.

`0001_init.sql` creates extensions and schemas only. Domain tables arrive with Milestone 2+.

Do not create a database per service yet.

## Catalog, store stock and agent data (migrations 0050–0054)

| Migration | Tables |
|---|---|
| `0050_shared_product_catalog.sql` | `shared.product_categories`, `products`, `product_fresh`, `product_style`, `product_tech`, `product_aliases`, `product_prices`, `outlet_products` |
| `0051_orders_order_lines.sql` | `orders.order_lines`, `orders.receipt_lines` |
| `0052_inventory_schema.sql` | `inventory.simulation_runs`, `stock_levels`, `stock_batches`, `stock_movements` (append-only ledger), `sales`, `sale_lines`, `stock_counts` |
| `0053_ai_schema.sql` | `ai.agents`, `observations` (raw, append-only), `insights`, `suggestions`, `suggestion_responses`, `agent_preferences`, `agent_runs` |
| `0054_append_only_deletes.sql` | Blocks `DELETE` and `TRUNCATE` on `inventory.stock_movements` and `ai.observations`, replaces the cascading foreign keys that reach the ledger with `RESTRICT`, adds `inventory.delete_simulation_run()` |

They are numbered from 0050 so they apply after the 0040–0045 migrations in open pull requests. They were tested together with every migration from those PRs.

- **Units.** A *pack* (crate, case, bag, carton) is what moves through ordering, loading and delivery, and matches `orders.order_units`. An *each* is one sellable item in a store. `shared.products.units_per_pack` converts between them; `inventory.*` counts eaches.
- **Append-only means no UPDATE, no DELETE, no TRUNCATE.** `inventory.stock_movements` and `ai.observations` reject all three with a trigger, and no foreign key cascades into the ledger (`stock_movements` -> `stock_batches`, `sale_lines`, `simulation_runs`, and the `simulation_run_id` links on `stock_batches`, `sales` and `stock_counts` are `ON DELETE RESTRICT`). Correct a mistake with a new `ADJUSTED` movement or a new observation. The only deletion path is `SELECT inventory.delete_simulation_run('<run id>')`: it refuses a run that does not exist or is recorded with `simulated = false`, and removes only rows with `simulated = true` tagged to that run (movements, sales and lines, batches, counts, observations, the insights that cite those observations, then the run row), resets `stock_levels` for the affected items from the ledger that remains, and returns the row counts. Inside, it sets the transaction-local `waypoint.allow_simulated_delete` and `waypoint.simulated_delete_run` that the delete triggers honour for that run only, and switches them off again before returning. It is not `SECURITY DEFINER`: the caller needs `DELETE` on the tables, so grant it only to operators. Anyone with that access could set the two settings by hand, but still only reaches simulated rows of one run, never real rows. Superusers can also bypass triggers with `session_replication_role = replica`; do not use it on these tables. `ai.observations.simulation_run_id` (added in 0054, a plain id) ties observations to their run; the seed sets it.
- **Cross-schema links** (for example `inventory.stock_levels.product_id` or `ai.suggestions.user_id`) are plain IDs, not foreign keys.
- **A3/A4 data** (habit patterns, automations) lives in `shared.*` from PR #34 and is not duplicated in `ai`.
- **Agents** never connect to PostgreSQL; they reach `ai` through insights-service.

### Seed data

- `seeds/catalog.sql`, generated by `scripts/generate-catalog-seed.py`: 24 categories, 114 products across Fresh, Style and Tech (in-store GTIN-13 barcodes, effective-dated LKR prices, everyday aliases), and 5,093 store-range rows. Store size, and so range width and daily sales targets, comes from each outlet's weekly order units in the official `deliveries_train.csv`.
- `seeds/inventory_history.sql`: eight weeks of trading for every store product, ending yesterday. It covers scheduled deliveries rounded to whole packs, first-expiry-first-out sales, expiry and breakage write-offs, and Sunday stock counts. It then builds weekly `ai.observations` and `ai.insights` (waste risk, stock-out risk and sales trends) from that ledger. Every row is `simulated = true` under the `seed-baseline` simulation run. It runs once (about two minutes); to regenerate, remove that run with `SELECT inventory.delete_simulation_run(id) FROM inventory.simulation_runs WHERE code = 'seed-baseline'` (about a minute) and seed again. OUT034 includes the demo case: 20 of 48 bottles of Fresh milk 1 L expired last week.

### Tests

`tests/append_only.sql` checks the rules above against a migrated database. It builds its own rows (`zt-*` runs, outlet `ZT-OUT`) in one transaction and rolls back, so it is safe on a seeded database. Run it after `apply.sh`:

```sh
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f database/tests/append_only.sql
```

It prints one `PASS` line per check and exits non-zero on the first failure. It covers: UPDATE, DELETE and TRUNCATE (including `TRUNCATE ... CASCADE` from a parent) refused on real and simulated rows; deleting a batch, sale line, sale or simulation run that has ledger rows refused; the delete exception not usable on real rows or another run's rows even when the settings are forced; `delete_simulation_run` refusing an unknown run and a run recorded as real data; and removing exactly the simulated rows of one run, leaving real rows and other runs alone.
